## Overview

The **Personal Finance Management System (PFMS)** is a robust, scalable platform designed to help users track their income, expenses, and budgets in real-time. Built with a **microservices architecture**, it addresses the limitations of monolithic financial applications by ensuring high availability, fault tolerance, and independent scalability of core components.

This project represents a shift from traditional monolithic design to a distributed system, handling complex data flows between authentication, budget management, notification, and reporting services.

## Architecture & Design

The system is composed of **14+ independent microservices**, each responsible for a specific domain. Communication is handled asynchronously via **RabbitMQ**, ensuring loose coupling and high throughput.

### Key Architectural Decisions

- **Event-Driven Communication:**  
  Used **RabbitMQ** to decouple services. For example, when a user exceeds a budget limit, the `Budget Service` publishes a `budget.exceeded` event, which the `Notification Service` consumes to send an alert. This prevents the `Budget Service` from being blocked by third-party email API latency.

- **API Gateway Pattern:**  
  Implemented **Kong API Gateway** as the single entry point for all client requests. This centralizes cross-cutting concerns such as:
  - **Rate Limiting:** Protecting services from DDoS attacks.
  - **Authentication:** Validating JWTs at the edge before requests reach internal services.
  - **Routing:** dynamically routing traffic to appropriate service instances.

- **Hybrid Database Strategy:**  
  - **PostgreSQL (Prisma):** Used for relational data requiring ACID compliance, such as User Accounts, Transactions, and Budgets.
  - **MongoDB:** Employed for unstructured data like Audit Logs and User Activity Streams, allowing for flexible schema evolution.
  - **Redis:** Implemented for caching frequently accessed data (e.g., exchange rates) and managing user sessions, significantly reducing database load.

### Infrastructure & DevOps

- **Containerization:**  
  Every service is containerized using **Docker**, ensuring consistent environments across development, staging, and production.
  
- **Orchestration:**  
  **Docker Compose** is used for local development orchestration, managing the startup order and networking of all 14 services, databases, and message brokers.

- **Security:**  
  - **Authentication:** Implemented centralized auth using **Better-Auth** with **JWT/JWKS**.
  - **Secret Management:** Environment variables and secrets are strictly managed to prevent leakage.

## Technical Challenges & Solutions

### Challenge: Distributed Transactions
Managing data consistency across microservices (e.g., deducting balance in one service and recording a transaction in another) was complex.
**Solution:** Implemented the **Saga Pattern** (orchestration-based) to ensure data consistency. If a step fails, compensating transactions are triggered to rollback changes.

### Challenge: Service Discovery
Hardcoding service URLs in a dynamic environment leads to fragility.
**Solution:** Kong API Gateway + Internal DNS handles service discovery, allowing services to scale up or down without client reconfiguration.

## Future Improvements

- **Kubernetes Deployment:** Migrating from Docker Compose to K8s for better production orchestration.
- **ELK Stack Integration:** Centralized logging for better observability.
- **gRPC:** implementing gRPC for inter-service communication to reduce latency compared to REST/AMQP.
